What Anubis is, and why it exists

Anubis is a reverse proxy that sits in front of a website and makes every visitor prove they spent some CPU before they get in. It was written because a lot of small sites were being flattened by scrapers and LLM crawlers: thousands of requests a second, each one cheap for the bot and expensive for the server.

The trick is not a CAPTCHA. A CAPTCHA asks "are you a human" and needs a human to answer. A proof-of-work gate asks "can you pay in electricity" — and the answer is verifiable arithmetic, so a machine can pass it. That is fine. The point is that scraping a site stops being free: instead of one cheap HTTP request per page, a bot now owes you a few hundred milliseconds of computing per page, per connection.

It does not make scraping impossible, and no honest gate claims to. It changes the economics. A browser also pays that price, which is why the difficulty is usually set to something a phone clears in a fraction of a second and why the client-side implementation matters: a page that needs 900 ms of wasm feels broken, and the same work at 200 ms does not.

Two consequences follow, and they shape everything in this repository:

  • The client side is real code. Anubis ships a WebAssembly module per algorithm and the browser runs it. Making that module faster is the difference between a gate users tolerate and one they bounce off.
  • The server side is real code too. Anubis re-computes the answer to check it. If the server's version is slow, every page view costs the site money — its own CPU, on the critical path.

The six words you need

challenge
The server's random payload, usually 32 random bytes, sent to the client as hex. It is unique per request, so an answer cannot be reused. Sometimes called the random data.
nonce
A number you are free to choose. You keep changing it and re-hashing until the result is good enough. "Number used once."
digest
The hash you computed — SHA-256, Argon2id or HashX output, depending on the algorithm. It is the thing being judged.
difficulty
How good the digest has to be. It is a count of leading zero bits for most algorithms and of leading zero nibbles for two of them, which is a 4x difference in meaning. See Algorithms; getting this wrong is the single most common source of confusion.
proof of work
The pair (challenge, nonce) that produces a good enough digest. Cheap to check, expensive to find — that asymmetry is the whole mechanism.
pass-challenge
The endpoint you send the proof to (/.within.website/x/cmd/anubis/api/pass-challenge). If it is right, you get an auth cookie and the real page; if not, you get another challenge.

One solve, step by step

Everything below is a real HTTP round trip. It helps to see it once in the open, because every tool in this repository is doing exactly this and nothing magic.

1. Ask for the page

You get a 200 with a challenge page instead of the page you wanted. Buried in it is a JSON blob:

<script id="anubis_challenge" type="application/json">
{"challenge":{"randomData":"6a1f8c2e…","id":"8f3c…","difficulty":4,…},
 "rules":{"algorithm":"sha256","difficulty":4}}
</script>

The solver parses this out of the HTML. It never executes the page's JavaScript.

2. Read the algorithm and the difficulty

These two numbers are the whole job description. sha256 with difficulty 4 means: find a nonce whose SHA-256 has 4 leading zero bits — 16 tries on average.

3. Loop over nonces until the digest qualifies

Hash, count leading zeros, compare. This is the part that takes time, and the part all the benchmarks on this site are about. A correct solver finds a nonce, not the nonce: every nonce below the one found is tested and rejected, so the work done is whatever the difficulty implied.

4. Submit the proof

A GET with the challenge id, your nonce, the response (your digest as hex), the redir you asked for, and an honest elapsedTime.

5. Keep the cookie, fetch the page

Success is a Set-Cookie for techaro.lol-anubis-auth, a signed JSON Web Token. Present it and the proxy treats you as passed, usually for hours.

Build it

One C compiler and Python 3.9+. No Node, no CUDA, no configuration file. The optional halves (GPU backends, GPU kernels, the Verilog side) are off unless you ask for them. 

git clone https://github.com/celikfana-lab/anubis-solver
cd anubis-solver
make -j8            # builds ./libanubis_solver.so
make test           # C core checks

If you prefer not to build anything, the Python CLI is the same tool:

pip install -r requirements.txt    # requests, for the CLI
python3 anubis_solver.py --help

On Debian/Ubuntu you may need build-essential and, for the accelerator backends only, libvulkan-dev or the Level Zero headers. If make fails, read the first error, not the last: the last is usually the linker complaining that the real error stopped something from being built.

Your first solve

The CLI is the shortest path, and it links the native engine — not the WebAssembly one. That distinction matters more than it looks, and it is visible in the timings below. 

python3 anubis_solver.py https://anubis.techaro.lol/

Instead of pointing at somebody else's site, you can put up a gate of your own in one command and solve that. It is the same exercise, it works offline, and you can turn the difficulty up and down yourself: 

# a page to protect, and a gate in front of it
mkdir -p /tmp/site && echo '<h1>PAST THE WALL</h1>' > /tmp/site/index.html
(cd /tmp/site && python3 -m http.server 8002 &) &
./betterAnusbis/betterAnusbis --listen :8099 --target http://127.0.0.1:8002 \
    --algorithm sha256 --difficulty 8

# in another shell: solve it
python3 anubis_solver.py http://127.0.0.1:8099/

This is real output, not an illustration:

solved sha256 difficulty=8 nonce=212 in 1.3 ms
HTTP 200 (69 bytes)
<html><body><h1>PAST THE WALL</h1><p>the real page</p></body></html>

The page came back, which is the proof: a rejected answer would have returned the challenge page again. Change --difficulty 8 to 20 and the same command reports something like nonce=2241431 in 142.0 ms — 12 more bits is about 4,096 times more attempts, and 142 ms against 1.3 ms is roughly what the arithmetic predicts once per-call overhead stops dominating.

Why "native" matters for those numbers. anubis_solver.py calls libanubis_solver.so, which uses SHA-NI and AVX2 kernels and can spread across cores. The browser has neither: it has WebAssembly. The same difficulty 20 task that takes 142 ms natively takes roughly 300 ms in the in-page wasm module — and that is the improvement this repository's wasm kernels exist to make, because a browser cannot install a native library.

Same thing, with the other two hard algorithms

# HashX: the program depends on the challenge, so it is compiled per challenge
solved hashx difficulty=20 nonce=685361 in 47.0 ms

# Argon2id: 19 MiB per attempt, so the difficulties are much smaller
solved argon2id difficulty=5 nonce=12 in 168.6 ms

Those two lines are the algorithms behaving exactly as designed. HashX is fast per hash but the program changes every time; Argon2id is slow per hash on purpose, which is what makes it resistant to being farmed out to a GPU.

How long should a solve take?

Difficulty is a count of leading zero bits, so the expected number of attempts is 2difficulty. Multiply by the per-hash cost and you have the expected time. This table uses the measured rates from Numbers, and keeps native and wasm apart because they differ by 2–7x depending on the algorithm:

A slower machine is proportionally slower. fast and slow count nibbles, not bits, so their difficulty number is 4x smaller for the same work.

sha256native, 1 core (~8 M/s)201,048,576≈ 0.13 s
sha256native, 4 threads (~20 M/s)2416,777,216≈ 0.84 s
sha256browser wasm (~3.4 M/s)201,048,576≈ 0.31 s
hashxnative JIT (~15 M/s)201,048,576≈ 0.07 s
hashxbrowser, compiled in the page201,048,576≈ 0.35 s
hashxbrowser, interpreted fallback201,048,576≈ 2.3 s
argon2idnative (~13 ms/hash)664≈ 0.85 s
argon2idbrowser wasm (~70 ms/hash)664≈ 4.5 s
fast / slownative (~8.3 M/s)5 nibbles1,048,576≈ 0.13 s
metarefreshany1none0.8 s of waiting

Read the argon2id rows twice. Sixty-four attempts taking seconds is not a bug — 19,456 KiB and two passes per attempt is the entire point of a memory-hard algorithm, and it is why deployments use difficulty 2–6 for it rather than 20.

Did it actually work?

"It exited 0" is not evidence. These are, in increasing order of how much they prove:

  • The page came back. The CLI prints the real content, not the challenge page. A gate that rejects you returns the challenge again.
  • The answer is accepted by a different implementation. wasm/verify-module.mjs hands our digest to the official Anubis WebAssembly module and requires it to accept. Two independent implementations agreeing is much stronger than one implementation not crashing.
  • The whole round trip is exercised. betterAnusbis/test-all-algorithms.sh starts a real gate on localhost, protects a real page, and asserts the protected text arrives — 11 checks, all six algorithms plus the honeypot. 
cd betterAnusbis && make && ./test-all-algorithms.sh
python3 tests/test_core.py
cd wasm && make verify-module    # our kernels vs Anubis's own modules
cd wasm && make verify-jit       # the runtime HashX compiler, 63 checks

Errors you will actually hit

__multi3 is undefined when linking the wasm kernels

HashX's 64×64→128-bit multiplies are written with __int128, which wasm has no instruction for and a -nostdlib build has no compiler-rt to supply. The build uses a portable 32-bit-half version instead (-DHASHX_NO_INT128). It is not a performance problem: those kernels are still faster than Anubis's. Installing libclang_rt.builtins-wasm32.a lets it link the other way and the machine code does not change, because wasm has no 128-bit multiply at any optimisation level.

There is no wasm-ld

clang can target wasm32 without the wasm linker being installed; you only find out at link time. On Debian/Ubuntu: apt install lld. Put it on PATH and the wasm targets build.

The challenge page comes back instead of the page

Your proof was rejected or your cookie was not sent. Check, in this order: the nonce is what you computed with, response is the digest of that nonce (not of another one), the id is the one from this challenge, and the cookie jar actually keeps techaro.lol-anubis-auth. A gate whose answer arrives after the challenge expired will also do this.

Difficulty seems 4x off

You are probably comparing a bit-based algorithm with a nibble-based one. fast and slow count leading zero nibbles; sha256, argon2id and hashx count leading zero bits. See units.

Nothing found, and it never stops

That is what a solver does: the search has no upper bound by design, and the current nonce space is searched until something matches. If it runs forever at a difficulty that should take a second, the per-hash rate is wrong — check you are not accidentally running the interpreter where you expected the compiled path (HashX is 7x slower interpreted), or the wasm module where you expected native.
