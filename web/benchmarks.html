How to read these numbers

Four rules, all of which cost me a wrong claim at least once:

  • Ratios within a run, not absolutes across runs. This laptop's governor and SMT sibling move identical code by up to 30%. Modules are loaded once and measured round-robin, so a slow minute hits every candidate equally. Every table below is one run; the same run measured twice can differ by 1.3x.
  • Count hashes, not calls. The search loop stops when it wins, and the number of attempts is random with mean 2difficulty. Timing N calls and dividing by N gives a number that depends on luck. The harness recovers the real attempt count from the nonce the search returned.
  • Warm up first. V8 compiles WebAssembly in two tiers. Timing the first hash after instantiation measures the tier-up compiler, not the kernel — that single mistake produced a "4x loss" that was mostly compilation.
  • Check the answer before believing the speed. A kernel that returns the wrong digest quickly is not fast, it is broken. Every timing in this repository is paired with a bit-exactness check against a reference: fill_vectors.txt for the Argon2id block, Anubis's own modules for the ABI, the C engine for everything else.

HashX — compiled from the challenge

Why the old one was twice as slow

Not the algorithm, and not the reference implementation: a build flag. The old module was built with -ffreestanding, which turns off the compiler's builtin memcpy. Inside the block function that means every 1 KiB copy became a call to a byte-at-a-time shim. The evidence is in the emitted code: the old binary contains 73 call $memcpy and no memory.copy; rebuilt without the flag it is the other way round.

The remaining gap was the reference block function: it expands each BLAKE2 round over the whole 1 KiB block inside a loop, so the 16 words a round touches are indexed by a loop variable and never reach registers. wasm/argon2_fill_fast.c gathers a round into a 16-word local with constant indices, which is worth another 1.25×. Everything else — H0, H′, index_alpha, the passes — still comes from the reference package, so the digests are unchanged and the test below proves it.

How this is checked: make verify-module runs ten random challenges through our module and hands each digest to Anubis's own module, which must accept it with its own anubis_validate. That is the test that would have caught the bad build; before it existed, nothing compared our binary against anything outside this repository.

Native engine

For scale, and because it explains why the browser extension exists:

workloadnativewasmratio
SHA-256, difficulty 20~0.13 s~0.31 s2.4×
Argon2id, per hash~13 ms~70 ms5.4×
HashX, per hash~0.07 µs0.31 µs~4×

Threads scale across nonces rather than inside a hash — p=1 is fixed by the challenge — which gives 2.11× on 2 workers and 3.75× on 4 for Argon2id, and 2.36× on 4 for HashX. GPU backends exist (CUDA, Level Zero, Vulkan) and are all opt-in; every GPU hit is re-verified on the CPU before it is accepted, so a broken driver cannot produce an invalid proof. Those tables are in SPEED.md because they are a different question.

Why the SIMD fill does not win

The obvious optimisation for Argon2id's block function is to do two 64-bit words at a time with wasm's v128. It was written, and it is bit-exact, and it does not beat scalar once the working set is the real 19 MiB. The reason is one instruction:

i64x2.extmul_low_i32x4_u is not vpmuludq. It multiplies adjacent i32 lanes, which in a natural u64 layout are the two halves of the same word — so each operand needs a gather (i8x16.shuffle) before the multiply, and V8 lowers the extmul itself with two more shuffles. That is four shuffle-port uops per fBlaMka, on a CPU with one shuffle port: 1,472 shuffle uops per block.

Measured from inside wasm, 128/128 reference vectors, min of nine runs. "Resident" is a hot cache; "scattered" is the real 19 MiB arena.
round implementationresidentscattered
scalar, register-resident0.77 µs0.80 µs
v128, rewritten1.21 µs1.53 µs
v128, first attempt1.04–1.08 µs1.25–1.30 µs

The rewritten version is 1.2–1.3× faster than the first attempt and still a tie with scalar when memory-bound, because the arithmetic is not the bottleneck at 19 MiB. What the exercise did find is that the plumbing around the round — unrolling the copy and the final XOR instead of looping 128 times — is worth 1.2–1.5×. That is not shippable in this driver (the C attempts came out 1.06× and 1.23× slower, and -msimd128 pessimises the round more than the plumbing saves), so the module keeps the scalar round and lets clang emit memory.copy for the copies.

Reproduce

# our wasm kernels vs Anubis's own modules (18 checks, both directions)
cd wasm && make verify-module

# the runtime HashX compiler: derivation, emission, digests, 63 checks
cd wasm && make verify-jit

# the Argon2id block function against the reference vectors
cd wasm && node verify-a2i.mjs && node bench-a2i.mjs

# every fill formulation, timed from inside wasm
cd wasm && node bench-fill-inmodule.mjs

# servers and clients, from /proc
python3 tools/bench-server-resources.py
node tools/bench-client-resources.mjs
node tools/bench-endtoend.mjs

The long-form versions, with the negative results and the per-run detail, are SPEED.md (all measurements) and wasm/README.md (the kernel-level argument). If a number here and a number there disagree, that is a bug — please open an issue.
