# Intel Xe assembly

`intelXe_sha256.xe` is the SHA-256 proof-of-work kernel written as Intel Xe
(gen12lp) assembly: one thread is eight lanes, each lane solves one nonce, 3,996
instructions, generated by [`tools/gen_xe_sha256.py`](../../tools/gen_xe_sha256.py).

This is the Intel card in the collection. The other machine-code artifacts are
`src/sass/` (NVIDIA SASS, disassembled from `nvcc` output) and the SPIR-V in
`src/vulkan/` and `src/levelzero/`. This one is *hand-built* rather than
disassembled, because no Intel toolchain on this machine emits gen text for us —
so it is verified the other way round: by executing its own instruction list.

| | |
|---|---|
| target | **gen12lp** (Xe-LP: Tiger Lake, DG1, Alder Lake-P), IGA platform `12p1` |
| assembler | **IGA 1.1.0-71af4e2**, from `intel-graphics-compiler` at `71af4e2` (2026-11-10), `visa/iga` |
| generated by | `python3 tools/gen_xe_sha256.py` |
| instructions | 3,996 |
| encoded size | 63,936 bytes (16 bytes per instruction) |
| registers touched | `r18` nonce, `r20`-`r27` working state, `r40`-`r55` `W[0..15]`, temporaries `r30`-`r39` and `r56`-`r63` |

## What is verified, and what is not

| check | how | result |
|---|---|---|
| the arithmetic | the generator executes the *emitted instruction list* in Python and compares the digest with `hashlib` | **exact** |
| the encoding | `iga64 -p 12p1 -a intelXe_sha256.xe -o x.krn` | **assembles**, 63,936 bytes, 3,996 instructions |
| the round trip | `iga64 -p 12p1 -d x.krn` on those bytes | 3,996 instructions back |
| execution on hardware | — | **not done** |

The last row is the honest gap. Vulkan and Level Zero consume SPIR-V and compile
it themselves; neither accepts a raw gen binary. Running this listing would need
either IGA's AUB (`aubinator`-style) replay or aioctl-level loading, and neither
is set up here. So this file proves the algorithm and the encoding, not a
throughput number, and **no performance claim is made from it**.

The arithmetic check is real, not circular: the generator builds a list of
instructions, writes the text from that list, and then a separate interpreter in
the same file walks the list and produces the digest, which must equal
`hashlib.sha256` of the same 48-byte message:

```
  interpret: f2bf82167d41fe1701711273d69d05f17793d6adb5bc30d290b448d1f5585f71
  hashlib  : f2bf82167d41fe1701711273d69d05f17793d6adb5bc30d290b448d1f5585f71  OK
  assemble : OK, 63936 bytes, 3996 instructions
```

## The ISA, in one screen

- A GRF is 32 bytes: **eight dwords, one per lane**. An instruction with execution
  size 8 operates on all eight at once, so one instruction is eight nonces' worth
  of work.
- Operands are written `r20.0<8;8,1>:ud`, meaning "read lane *i* from `r20.i`,
  stride 8, width 1". That region is what makes a register a per-lane vector
  instead of a scalar.
- **There is no rotate instruction.** Every `ror` in SHA-256 costs `shr` + `shl` +
  `or`, which is where most of the file goes: 576 rotations, 1,728 instructions.
- `lzd` (leading zero detection) is the hit test; `cmp (ge)` sets a flag and
  `(W) jmpi` takes the branch past the write on a miss.
- The public description of the encoding is Intel's
  [Open-Source Programmer's Reference Manuals](https://www.intel.com/content/www/us/en/docs/graphics-for-linux/developer-reference/1-0/hardware-specs.html)
  for the 11th-generation iGPUs, which is the same gen12 family as this laptop's
  Alder Lake-P part; IGA is the encoder of record for the mnemonic syntax used
  here.

## Instruction mix

| opcode | count | why |
|---|---:|---|
| `shr` | 672 | 576 from rotations, 96 from the two message-schedule shifts |
| `xor` | 640 | `ch`, `maj`, both `Σ` functions, both `σ` functions |
| `add` | 600 | round sums, message schedule, final IV add |
| `shl` | 576 | the other half of every rotation |
| `or` | 576 | the join of every rotation |
| `mov` | 545 | 8 prologue, 16 message block, 8 IV, 512 state rotation, 1 null |
| `and` | 320 | `ch` and `maj` |
| `not` | 64 | one per round, for `~e` |
| `lzd`, `cmp`, `jmpi` | 1 each | the hit test |

## Why it is longer than the SASS card

`src/sass/nvidiaT4_sha256.sass` is 2,024 instructions for the same algorithm.
This one is 3,996, and the difference is informative rather than embarrassing:

- **rotations.** SASS has `SHF` (funnel shift, one instruction); gen ISA does not.
  576 rotations × 3 instructions instead of × 1 is +1,152.
- **register renaming.** ptxas alternates two state sets so the `h=g; g=f; ...`
  shuffle disappears. This listing does it literally: 8 `mov`s per round, 512 in
  total.
- **scope.** The T4 kernel receives an 8-word midstate and builds only a small
  tail; this file starts from the IV and builds a complete 64-byte block from
  immediates, so it has a message to hash without needing memory.

So roughly 1,664 of the extra 1,972 instructions are "this ISA has no rotate" and
"the generator takes the simple way out". Both are fixable:

- alternate two state register sets per round → −512 instructions, no other
  change;
- rotations via `shl`/`shr` on a value already in the right register can sometimes
  be shared between `Σ` terms, which the generator does not attempt;
- `lzd` + `cmp` could be replaced by comparing against a precomputed mask when the
  difficulty is known at compile time, as it is for a single challenge.

None of those are done, because none of them can be measured on this machine, and
an unmeasurable optimisation is a claim, not a result.

## Reproducing

IGA is buildable on its own out of IGC. Only two subtrees are needed, so a sparse
clone keeps it small (~35 MB):

```sh
git clone --depth 1 --filter=blob:none --sparse \
    https://github.com/intel/intel-graphics-compiler.git igc
cd igc && git sparse-checkout set visa/iga inc
cd visa/iga && mkdir build && cd build
cmake .. -G Ninja -DCMAKE_BUILD_TYPE=Release && ninja
# iga64 lands in build/IGAExe/iga64
```

Then, from the repository root:

```sh
export IGA64=$(pwd)/igc/visa/iga/build/IGAExe/iga64
python3 tools/gen_xe_sha256.py              # emit, interpret vs hashlib, assemble, round trip
python3 tools/gen_xe_sha256.py --no-assemble
```

Platform names matter and are not obvious: IGA rejects `GEN12LP` and wants
`12p1` for Xe-LP (`iga64 -h=p` lists the rest). A size-1 instruction must carry
ChOff `M0` — the lane is chosen by the destination subregister, which is why the
prologue writes `r18.0`, `r18.1`, … rather than using `M0`, `M1`, ….

## What the library actually uses

Nothing here is loaded at runtime: `src/levelzero/` and `src/vulkan/` ship SPIR-V
and let the driver compile it. This directory is the readable record of what that
compilation has to do, and the Intel half of the machine-code collection.
