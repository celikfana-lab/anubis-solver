# Intel Xe assembly

Two listings of the same SHA-256 proof-of-work kernel, one per compiler, and
then the same treatment for HashX ([below](#hashx-the-same-treatment-for-the-other-algorithm)):

| file | who wrote it | instructions | ran on the GPU? |
|---|---|---:|---|
| `intelXe_sha256.xe` | `tools/gen_xe_sha256.py`, hand-built | 2,846 (unrolled) | **yes, through `build/xe-loader`** |
| `intelXe_sha256.igc.xe` | **IGC**, Intel's compiler, extracted from a Zebin | 1,711 (looped) | **yes, 195.2 M hashes/s** |

Both produce the same digest. That is the useful part: the hand-written listing
is verified by *its own* arithmetic, and the vendor's listing is verified by
*running*, and the two agree on the answer.

## HashX, the same treatment for the other algorithm

`intelXe_hashx.xe` is HashX written for the same target: 30,260 instructions,
484,160 bytes, one thread = 8 lanes = 8 nonces.

HashX is not a hash function with a fixed message. A challenge is a SipHash key
plus a **program** of up to 512 instructions over eight 64-bit registers; the
program is generated from the challenge bytes, expanded into the register file
by SipHash-2-4, run, and mixed back with SipHash. `src/hashx/hashx.c` is the
reference, and `hashx_export()` already hands a GPU the keys and the program in
exactly the shape a kernel needs.

| | |
|---|---|
| generated by | `python3 tools/gen_xe_hashx.py` |
| shape | **JIT**: the keys and the program are baked in as immediates, so the listing has no memory reads, no descriptors and no dispatch |
| instructions | 30,260 (512 program ops, each 64-bit op expanded into 32-bit lane arithmetic, plus 16 masked re-runs) |
| encoded size | 484,160 bytes |
| registers | `r20..r35` = `r0..r7` as (lo, hi) pairs of a u64, `r120/r121` = nonce, `r40..r111` = temporaries |

### Three things a GPU port of HashX has to solve

1. **64-bit arithmetic on 32-bit lanes.** Every HashX op works on u64: multiply
   low, unsigned and signed multiply high, rotate, shift, add with carry. There
   is no 64-bit multiply on gen12lp, and `mul` is 32x32 low. The listing builds
   every 64-bit product out of four 16-bit-limb multiplies, which are exact for
   any operand and therefore do not depend on `mul`'s signedness or its high
   half. Carries are explicit (`cmp` + a predicated add), not a condition code.
2. **Divergent control flow.** A HashX program branches every 32 instructions,
   each branch jumps back to the start of its own 16-instruction block, and
   `be` (branch_enable) means **at most one** is ever taken -- but *which* one
   differs per nonce, and eight lanes cannot take different jumps. The listing
   therefore runs each block twice: once on the straight path, and once on a
   copy guarded by that block's predicate, then puts back the lanes that did not
   fire. The C's single `be` flag becomes a per-lane `fired` mask.
3. **Nothing to read.** Baking the program in is what makes this page-sized
   listing possible at all: a kernel that read the program from a buffer would
   need `send.dc1` messages and surface descriptors, which is what the OpenCL
   kernel in `src/levelzero/hashx_l0.cl` gets from the compiler.

### Verified how

```sh
cc -O2 -o /tmp/hxe tools/xe-hashx-export.c  src/hashx/hashx.c -Isrc/hashx
cc -O2 -o /tmp/hxs tools/xe-hashx-stages.c  -Isrc/hashx

python3 tools/gen_xe_hashx.py --selftest   # 64-bit primitives vs Python
python3 tools/gen_xe_hashx.py --stages     # register file vs the C interpreter
python3 tools/gen_xe_hashx.py --assemble   # the listing, checked with IGA
```

| check | result |
|---|---|
| the 64-bit primitives | add, sub, xor, shifts, rotates (all ten the SipHash uses), multiply low/high, signed multiply high: **exact** against Python's integers, ten random and boundary cases each |
| the register file | after the SipHash expansion and after the 512-instruction program, `r[0..7]` match `src/hashx/hashx.c` for all **8 lanes** |
| the digests | all 8 match the reference (`nonce 0..7`), which is the only claim that counts |
| the encoding | `iga64 -p 12p1 -a`: assembles, 30,260 instructions, 484,160 bytes |
| **hardware** | **not run**. Same reason as the SHA-256 listing: this needs a Zebin splice, and this listing also has no result store (the digest ends in registers, `r[0]^r[4] .. r[3]^r[7]`), so a run would prove execution, not output |

### What it cost, written down

- **gen12lp has no `sub`.** A subtraction is `add` with a negated source
  (`-r5.0<8;8,1>:ud`). IGA says "invalid mnemonic" and is right.
- **There are two flag registers, `f0` and `f1`.** `f2` and `f3` assemble their
  operands and then die in the encoder with "GED_SetFlagRegNum: invalid value".
- **The branch resumes at `target + 1`, not at `target`**: the C does
  `i = target` and then the `for` loop's `++i`.
- **SIPROUND is written with `ROTL`**, so every rotation in this file is
  `rol(n)` = `ror(64-n)`; writing `ror(n)` because the OpenCL kernel spells it
  `rotr` is a wrong digest that looks like a wrong multiply.
- **Aliasing, twice.** `add64(d, a, b)` with `d == a` loses the carry if the
  compare runs after the write, and `ror64(d, d, n)` loses the low half if it
  writes one half before reading the other. Both were found by the self-test
  above, in seconds, which is the argument for having one.

## The hand-written listing

| | |
|---|---|
| target | **gen12lp** (Xe-LP: Tiger Lake, DG1, Alder Lake-P), IGA platform `12p1` |
| assembler | **IGA 1.1.0-71af4e2**, from `intel-graphics-compiler` at `71af4e2` (2026-11-10), `visa/iga`; also packaged as `/usr/bin/iga64` by `libigc2-tools` |
| generated by | `python3 tools/gen_xe_sha256.py` |
| instructions | 2,846 |
| encoded size | 45,536 bytes (16 bytes per instruction) |
| registers | `r18` nonce, `r20`-`r27` state, `r40`-`r55` `W[0..15]`, temps `r30`-`r39`/`r56`-`r63` |

| check | how | result |
|---|---|---|
| the arithmetic | the generator executes the *emitted instruction list* in Python and compares the digest with `hashlib` | **exact** |
| the encoding | `iga64 -p 12p1 -a intelXe_sha256.xe -o x.krn` | **assembles**, 45,536 bytes, 2,846 instructions |
| the round trip | `iga64 -p 12p1 -d x.krn` | 2,850 instructions back |
| execution on hardware | `build/xe-loader` patches the listing into an IGC Zebin and loads it through OpenCL | **yes**, see below |

Execution used to be the gap: Vulkan and Level Zero consume SPIR-V and compile it
themselves, and there is no Level Zero driver on this machine. It is now solved the
rude way, by splicing the listing into a Zebin that IGC produced; see "Running the
hand-written listing" below.

## IGC's own code, and the GPU run

`intel-opencl-icd` gives a real Intel OpenCL stack on this laptop (OpenCL 3.0 NEO,
96 EUs). [`tools/xe-sha256-opencl.c`](../../tools/xe-sha256-opencl.c) runs the same
algorithm through it and asks for the compiled binary:

```
device: Intel(R) Iris(R) Xe Graphics
total=1 nonce=0 digest=f2bf82167d41fe1701711273d69d05f17793d6adb5bc30d290b448d1f5585f71
igc binary: 37976 bytes -> /tmp/igc-sha256.bin
throughput: 195.2 M hashes/s (4194304 nonces in 0.021 s, best of 5)
```

- the digest is `hashlib.sha256` of the same 48-byte message, so the kernel is
  correct on the GPU;
- the binary is a **Zebin ELF**: `.text.sha256_pow` at 0x40, 20,544 bytes, and
  `.data.const` holding K (64 words) as constant data rather than immediates;
- disassembling that section with IGA gives 1,711 instructions, saved as
  `intelXe_sha256.igc.xe`.

For comparison on the same GPU and the same kernel: the WebGPU path (ANV
compiling WGSL, SIMD8) measures 70.6 M hashes/s, IGC's native compile measures
195.2. Same hardware, same work, 2.8x apart — that is a compiler and SIMD-width
difference, not a GPU difference.

## The ISA, in one screen

- A GRF is 32 bytes: **eight dwords, one per lane**. An execution size of 8
  operates on all eight at once, so one instruction is eight nonces' worth of
  work.
- Operands are written `r20.0<8;8,1>:ud`, meaning "read lane *i* from `r20.i`,
  stride 8, width 1".
- **`ror` and `rol` exist** and are one instruction each. An earlier version of
  this file claimed gen ISA had no rotate and expanded every rotation into
  `shr`+`shl`+`or`; that was wrong, cost 1,152 instructions, and was caught by
  reading IGC's output for the same kernel, which uses `rol`.
- `lzd` is the leading-zero test; `cmp (ge)` sets a flag and `(W) jmpi` branches
  past the write on a miss.
- The public description of the encoding is Intel's
  [Open-Source Programmer's Reference Manuals](https://www.intel.com/content/www/us/en/docs/graphics-for-linux/developer-reference/1-0/hardware-specs.html)
  for the 11th-generation iGPUs (the same gen12 family as this Alder Lake-P part).

## Instruction mix, ours

| opcode | count | why |
|---|---:|---|
| `xor` | 640 | `ch`, `maj`, both `Σ` and both `σ` functions |
| `add` | 600 | round sums, message schedule, final IV add |
| `ror` | 576 | 384 in the rounds, 192 in the message schedule |
| `mov` | 545 | 8 prologue, 16 block, 8 IV, 512 state shuffle, 1 null |
| `and` | 320 | `ch` and `maj` |
| `shr` | 96 | the two `σ` functions, one shift each |
| `not` | 64 | one per round, for `~e` |
| `lzd`, `cmp`, `jmpi` | 3 | the hit test |

## Why ours is 2,844 and IGC's is 1,711

- **Ours is fully unrolled**: 64 rounds as straight-line code, like the CUDA
  kernel in `src/cuda/`. IGC emits loops and re-enters them, which is why its
  code is a third shorter and still faster.
- **Ours keeps K as immediates**; IGC reads it from `.data.const` with
  `send.dc1` (190 of them), trading instructions for constant-bandwidth.
- **Ours does not rename registers between rounds**: 8 `mov`s per round, 512 in
  total. IGC rotates through register pairs.
- **Scope**: IGC takes the message from buffers and processes 16 lanes at a time;
  ours builds one 48-byte message inline for 8 lanes.

The 512 moves are the easy win — alternate two state sets and the listing drops
to about 2,330 — and it is not done, because an optimisation that cannot be run
here is a claim rather than a result.

## Running the hand-written listing

`tools/xe_load.c` (`make xe-loader`) executes this file. OpenCL is the only Intel
runtime here that loads machine code, and it wants a Zebin: an ELF whose
`.text.<kernel>` section holds the instructions and whose `ze_info` section
describes the arguments and the dispatch payload. So the loader compiles a
reference kernel with IGC, keeps IGC's metadata, appends our IGA output at the
end of the file and repoints the section header at it:

```
hand-written kernel: 45536 bytes, 2846 instructions
reference zebin: 37976 bytes
patch: .text.sha256_pow was 20544 bytes at 0x40, now 45536 bytes at 0x9480
patched image loaded and built
hand-written kernel ran: 0.000 s for 65536 nonces = 155.1 M hashes/s
results buffer: total=0 nonce=0 (expected 0: this listing has no store)
IGC's kernel, same dispatch: 0.001 s = 50.5 M hashes/s (0.33x)
```

**The first version of this faulted**, and the reason is worth writing down: a
gen kernel has to end with an end-of-thread message. Without one the thread never
retires, `clFinish` returns `CL_OUT_OF_RESOURCES`, and it looks like a driver
crash rather than a missing instruction. IGC's own kernel ends with

```
(W) send.ts (1|M0) null r127 null 0x0 0x02000010 {EOT}
```

and the generator now emits the same. That the fault appeared with our text and
disappeared when only that instruction was added is also the proof that our
instructions are what runs: IGC's code already had an EOT and still has one.

Read the speed carefully. **It is not a race.** The generated kernel ignores the
`base` and `count` arguments and computes the same eight nonces in every
workgroup, at eight lanes, with no result store at all (`results buffer: total=0`
is the listing admitting it). IGC's kernel reads its arguments, runs 16 lanes and
writes digests back. The numbers above say "the code executes", not "our code is
faster than IGC's" -- for that the generator needs to consume the arguments and
store results, which is the next piece of work, not this one.

## Reproducing

IGA builds standalone out of IGC; only two subtrees are needed (~35 MB):

```sh
git clone --depth 1 --filter=blob:none --sparse \
    https://github.com/intel/intel-graphics-compiler.git igc
cd igc && git sparse-checkout set visa/iga inc
cd visa/iga && mkdir build && cd build
cmake .. -G Ninja -DCMAKE_BUILD_TYPE=Release && ninja   # -> build/IGAExe/iga64
```

Then:

```sh
export IGA64=$(pwd)/igc/visa/iga/build/IGAExe/iga64
python3 tools/gen_xe_sha256.py       # emit, interpret vs hashlib, assemble, round trip
make xe-loader                       # build the OpenCL loader for our listing
./build/xe-loader --text /tmp/intelXe_sha256.krn --count 65536

# and the vendor comparison, on a machine with Intel OpenCL:
gcc -O2 -o /tmp/clrun tools/xe-sha256-opencl.c -lOpenCL && /tmp/clrun
```

Two syntax traps, both found by assembling: the platform string is `12p1`, not
`GEN12LP`; and a size-1 instruction must carry ChOff `M0`, with the lane chosen
by the destination subregister (`r18.0`, `r18.1`, …).

## What the library uses

Nothing here is loaded at runtime: `src/levelzero/` and `src/vulkan/` ship SPIR-V
and let the driver compile it, and the newly available OpenCL path
(`src/opencl/`, not wired yet) would go through IGC the same way the harness
above does. This directory is the readable record of what that compilation does,
with both the vendor's answer and a hand-written one to compare it against.
