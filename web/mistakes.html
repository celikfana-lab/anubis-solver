What we got wrong

Every claim below was made in this repository's documentation, was measurably false, and was corrected. They are kept as a list rather than quietly edited away, because the mistake behind each one is the kind you will make yourself the first time you measure a proof-of-work loop — and because a benchmark page that admits nothing is worth the same as one that admits everything.

The pattern. Six claims, four of them produced by the same cause: comparing two things that were not the same thing. Different artefacts, different warmth, different counting, different units. Speed claims are easy to make and hard to hold; these are the ones that did not hold.

1. "wasm SIMD has no 64-bit multiply"

Said: the SIMD proposal has no i64x2 multiply, which is why an Argon2id SIMD kernel cannot be written in wasm.

True: i64x2.mul exists and has since the proposal shipped. What does not exist is the unsigned 32×32→64 widening multiply in Rust's stable core::arch::wasm32 — only the signed form, i64x2_extmul_low_i32x4. The wasm instruction i64x2.extmul_low_i32x4_u is right there; the Rust binding is not.

Cause: inferring the instruction set from the language binding. The instruction you can name from your language is not the instruction set.

Found by writing the kernel in WAT instead, where the unsigned opcode is one instruction, and watching it assemble.

2. "Our C kernel is 0.01 µs faster than hand-written WAT"

Said: clang's C was marginally faster than the generated WAT.

True: in the same interleaved run it was 0.06 µs slower, which is inside the noise. The honest claim is "within 4%, a tie" — not a direction.

Cause: reading two numbers from two runs and subtracting them. A 0.01 µs difference on a 1.8 µs measurement is 0.5%; the run-to-run spread on this machine is 30%.

3. "Our HashX interpreter does 1.7 M hashes/s"

Said: the WebAssembly interpreter ran at about 1.7 M hashes/s, making the compiled path "1.6× faster".

True: the interpreter does 0.43–0.46 M hashes/s. The 1.7 M figure was the native C engine from a different table two sections away. Measured properly, compiling is 7× the interpreter, not 1.6×.

Cause: a number copied into the wrong row. The ratio was so implausible — an interpreter within 60% of a compiler — that it should have been caught by arithmetic rather than by measurement.

4. "Argon2id is at parity with Anubis"

This one is two mistakes wearing one coat.

Said: our Argon2id module is at parity with Anubis's.

True, part one: the claim was measured on the block function (1.7–1.9 µs against their implied 1.8–2.0), then applied to the whole module. The module was 2.2× slower. Two different artefacts, one sentence — and the sentence was true of one of them.

True, part two: even that module number was mostly a miscompile. The shipped binary had been built with -ffreestanding, which disables the compiler's builtin memcpy and turns every 1 KiB block copy into a call to a byte-at-a-time shim. Rebuilt without the flag, the same sources run at 86 ms instead of 162. With the block function rewritten to keep each round in registers, 65–75 ms — 1.02–1.05× faster than Anubis's.

Cause: (a) conflating an inner loop with a program; (b) never having compared our compiled artefact against anything outside the repository. The second is now impossible: make verify-module hands our digests to Anubis's own module and requires it to accept them.

The lesson worth stealing: a build flag that "looks like it belongs" in a -nostdlib project can cost 2×. The way to find out is to read the emitted instructions — call $memcpy where you expect memory.copy — not to reason about the flag's description.

5. "Nothing here compiles a challenge in the browser"

Said: the generate-WAT-and-assemble path was a build-time experiment for one fixed challenge; real challenges would have to be interpreted.

True: that was a statement about the toolchain, not about what was possible. Emitting wasm bytes is not hard; it just was not written yet. wasm/hashx_jit.mjs now derives the program and emits the module in plain JavaScript, so any challenge is compiled in the page with no wat2wasm and no server round trip.

Cause: describing a limitation of the implementation as if it were a limitation of the approach. Worth flagging because that is the easiest way to accidentally be wrong on a documentation page: "nothing does X" usually means "we have not done X".

6. "Halving the multiplies will make the SIMD fill faster"

Said: processing two 64-bit words per v128 register halves the multiply count, so the fill should be materially faster.

True: it is slower than scalar, and now the reason is measured: the unsigned widening multiply needs both operands' low halves gathered into adjacent i32 lanes first, and V8 lowers the widening multiply itself with two more shuffles. Four shuffle-port uops per fBlaMka, 1,472 shuffle uops per block, on a CPU with one shuffle port. The scalar round wins.

Cause: counting the arithmetic and ignoring the data movement needed to feed it. "Fewer multiply instructions" is not "fewer cycles" when the operands have to be repacked first.

The one that nearly shipped

Worth recording because the process worked. A rewrite of the fill that skipped one of its two 1 KiB scratch arrays on the first pass measured 1.02× faster. It was also wrong: when the "XOR over the old value" flag is clear the value you must keep is ref ^ prev, not zero, and the rewrite dropped it. Modules were built, and make verify-module rejected the digests before anything was released.

A 2% win is not worth a wrong proof, and speed without a correctness check is how you ship one.

Six rules for measuring a proof-of-work loop

  1. Count attempts, not calls. The search stops when it wins, and the attempt count is exponential. Recover it from the nonce, or force a difficulty that never hits.
  2. Warm up the compiler. WebAssembly engines tier up. First-call timing measures compilation.
  3. Interleave the candidates. Load every variant once and measure them round-robin in one process. Sequential runs measure the machine's mood.
  4. Report ratios from one run. Absolute hashes/s move 30% with the governor, the SMT sibling and the weather. The ratio is the result.
  5. Verify before you celebrate. Compare against a reference that is not your own previous binary. Two independent implementations agreeing is evidence; one implementation not crashing is not.
  6. Say which artefact you measured. "The fill core", "the module", and "the search loop" are three different claims, and conflating them is how mistake 4 happened.

If you find a claim on this site that does not reproduce, open an issue — that is the same mechanism that produced this page.
