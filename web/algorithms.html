The six algorithms

Anubis can ask for six different proofs. They are not variations on a theme: one costs nothing, one costs a fraction of a millisecond, one costs 19 MiB and about 70 ms per attempt. Choosing the wrong one makes a site either useless or unusable, so the useful question is "what does this difficulty number actually buy me".

Difficulty is two different things

This is the trap worth reading first. Anubis measures difficulty in leading zero bits for the WebAssembly algorithms and in leading zero nibbles (hex digits, 4 bits) for the JavaScript ones. So:

Anubis's own source checks the JS ones with strings.HasPrefix(response, strings.Repeat("0", difficulty)), which is literally "this many zero hex digits".
algorithm familyunitdifficulty 5 meansexpected attempts
fast, slownibbles20 zero bits220 ≈ 1.05 M
sha256, argon2id, hashxbits5 zero bits25 = 32

A difficulty of 5 is a light tap for a wasm algorithm and a million hashes for a JS one. Nothing in the protocol stops you from treating them as the same scale; that is a policy question, and the answer is "do not".

Each one, in detail

fast — the original JavaScript proof

The client hashes the challenge string with the decimal nonce appended, and needs enough leading zero hex digits. Anubis's browser implementation uses crypto.subtle.digest where it is available (so it is native SHA-256, not JS arithmetic) and falls back to a JavaScript SHA-256 in Firefox and Goanna, spread over workers.

It is cheap, it has been there from the start, and every Anubis client speaks it. It is also the weakest of the six: a single SHA-256 core does 8 M+/s, so difficulty 6 is under a second on a laptop and a bot farm barely notices.

slow — not slower; deprecated

Anubis's own dispatch table says, in a comment: slow: fast, // XXX(Xe): slow is deprecated, but keep this around in case anything goes bad. The server registers both names and validates them identically. There is no extra work and no different digest.

If you are writing new policy, pick fast or one of the WebAssembly algorithms. slow exists for policies that already name it.

sha256 — the WebAssembly default

A WebAssembly module hashes the raw challenge bytes with a 4-byte nonce and counts leading zero bits. Because the loop lives inside the module, the browser pays one call per search rather than one call per hash — which is why a good client is 2x Anubis's module here and still only 3.4 M/s, an order of magnitude behind a native SHA-NI kernel.

This is the sane default for general web traffic: predictable cost, no memory blow-up, works in every browser that ships WebAssembly.

hashx — a program per challenge

The most interesting one. The challenge bytes seed a small deterministic compiler that emits a 512-instruction program over eight 64-bit registers — mixing multiplies, rotates, adds and one guarded branch — and the client runs that. The digest is the finalised register state.

Two consequences. First, the program differs per challenge, so a fixed hardware implementation cannot be pre-baked. Second, because the program is fixed for the whole challenge, a client can compile it to native code or to WebAssembly and stop interpreting — which is exactly what this repository does, for a 7x gain over interpreting:

argon2id — memory-hard, and it means it

One full Argon2id hash per attempt: m=19456 KiB, t=2, p=1, 32-byte output. The challenge bytes are the password and an 8-byte encoding of the nonce is the salt. Small detail with a purpose: the nonce is encoded little- or big-endian depending on whether the challenge's last byte is at or above 0x80, a deliberate asymmetry to make GPU implementations more annoying.

19 MiB per attempt is the whole point. You cannot dodge it with a GPU because the algorithm is bound by memory bandwidth, not arithmetic — and the same property is why the browser feels it. At ~70 ms per attempt in WebAssembly, difficulty 6 is about four and a half seconds of a phone's life.

Choose the difficulty here, not by habit. A difficulty of 20 is a normal sha256 setting and roughly a million times too much for argon2id. Deployments use 2–6, and 6 is already a noticeable pause.

metarefresh — a proof of patience

No hashing at all. The page waits difficulty × 800 ms and then follows a meta refresh to the pass-challenge endpoint with the challenge echoed back. Anubis uses it to tell "a browser that will run a redirect" from "a client that will not".

It costs the client nothing but wall-clock time, so it is nearly free to bypass for anything that implements a timer. Treat it as a bot filter, not a proof of work.

Which should you deploy?

if you wantusebecause
the least friction that still filters dumb bots fast d4–5, or metarefresh sub-millisecond for real visitors; blocks clients that will not run JS at all.
a good general default sha256 d18–22 0.1–0.5 s in the browser, no memory pressure, universally supported.
to cost scrapers more per page hashx d15–20 the per-challenge program resists fixed-function hardware, and a compiled client keeps it fast for humans.
to make GPU farms uneconomic argon2id d3–6 memory-hard by construction; 19 MiB per attempt is not parallelisable away.
to protect an API, not a page sha256 or hashx, low difficulty there is no browser to be nice to; keep the cost where a real client can absorb it.

Two rules that survive every configuration: test it on the slowest device you care about, and remember that difficulty is a cost you are charging your own users first.

Why difficulty numbers are not comparable

"We use difficulty 20" says nothing until you name the algorithm and, for the JavaScript ones, whether you mean nibbles. Work it out instead: 

expected hashes = 2 ^ difficulty          # bits
expected hashes = 2 ^ (4 * difficulty)    # nibbles

expected seconds = expected hashes × cost per hash

With this repository's rates:

Same nominal difficulty, wildly different work. Times are expected values; the distribution is exponential, so any single solve can be several times the average in either direction.

That last row is not a hypothetical: putting a sha256 difficulty into an argon2id rule is the classic way to make a site unreachable. It is also why the tiers in Anubis's documentation are per algorithm and not one scale.
