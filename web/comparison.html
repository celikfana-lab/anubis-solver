betterAnusbis vs Anubis

Two ways to put the same wall up. This page is the honest comparison: where one is faster, where the other has features the first does not, and which situations should send you to Anubis.

Not a fork. betterAnusbis speaks Anubis's protocol — same routes, same challenge JSON, same cookie name — so any Anubis client works against it unchanged. That is what makes the comparison meaningful rather than apples to oranges.

Why the gap is that large: Anubis is a Go service whose runtime and dependencies cost ~45 MB before it does anything, and it re-checks each answer by running the same WebAssembly module inside wazero. betterAnusbis is one C program with a 32-byte secret and a small trap table, and it verifies with libanubis_solver.so — the same engine the CLI uses.

What Anubis does better

Being clear about this is more useful than a table that only points one way.

  • Policy is a language there and a list here. Anubis can match on weights, expressions and per-rule difficulty, and reads a YAML config. betterAnusbis has three actions and first-match-wins. If you need "score this user agent 4 and this one 20", that is Anubis.
  • Multiple replicas. Anubis keeps challenge state in pluggable backends, so two instances behind one load balancer agree about what has been consumed. betterAnusbis keeps it in memory: one process, or --stateless with weaker guarantees.
  • Production web serving. Anubis is a Go HTTP server with HTTP/2 and keep-alive. betterAnusbis reads one request, answers it and closes. Put it behind nginx or caddy; do not make it the only thing in front of a streaming app.
  • An imprint page, a make-challenge API and the surrounding tooling. Those exist there and not here.
  • It is the reference. When Anubis changes its challenge format, Anubis is right by definition. This repo's tests compare against Anubis's own modules precisely because that is the authority.

What betterAnusbis does better

  • It is small. 2.1 MB and one thread, against 44–46 MB and 17–19. On a $5 VPS, or next to other services, that is the difference between fitting and not fitting.
  • Verification is half the cost. 1.25 ms against 2.3–2.8 ms, on the critical path of every page view.
  • It is one C file. You can read the whole gate in an afternoon, and make is one cc line. Nothing hides in a dependency tree.
  • The client side is faster. The wasm kernels are 1.8–2.1× Anubis's for SHA-256 and 7–8× for HashX, which is time a real visitor does not spend waiting.
  • It comes with a solver. The same library verifies and solves, so a test can establish that a challenge is passable end to end.

Which should you use?

situationpick
existing Anubis deployment, YAML policies, several replicasstay on Anubis — nothing here replaces its policy engine or backends
small site, one box, want the wall up todaybetterAnusbis — one binary, one flag per decision
you need the challenge solved programmatically in CIthis repo's CLI or library, against either server
you are studying how the six algorithms behaveeither — both are protocol-compatible, so the numbers transfer
you want the browser to spend 0.3 s instead of 2.3 s on HashXserve this repo's kernels (--web), or use the extension
